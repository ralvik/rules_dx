# Quality Result Protocol

## Purpose

Quality actions communicate completed analyzer results to Bazel evaluators and the `dx`
CLI through one internal binary Protobuf contract. This protocol is distinct from the
public NDJSON and standard-report API in [Output Protocol](../cli/output-protocol.md).

## Transport

Every lint, typecheck, or format target/capability pipeline action emits one bounded binary
Protobuf result message. Non-mutating audit may emit one message per target/tool action. The
checked-in [`quality/result.proto`](../../quality/result.proto) is the source of truth:
field/enum numbers and reserved ranges are frozen under [O18](../open-decisions.md) with
this initial implementation. Bazel generates the Rust crate `result_proto` via
`//quality:result_proto_rs`, and `//rust/quality_result` implements the result-side
validation, BLAKE3 digest, and deterministic codec (`validate`, `encode_validated`,
`decode_validated`). The pipeline producer is `//rust/quality_runner` (M03 WP2b);
evaluators and collectors land in M03 WP3, so do not build them against the
semantic prose below until then. The sole
stable public capability output group is `dx_results`; it contains each result and an enabled
per-result validation marker. No invocation-level aggregation action exists.

The CLI discovers requested artifacts through BEP named sets. It does not walk
`bazel-out`, inspect action-cache internals, or maintain a second artifact index. Bazel
materializes requested remote outputs before local rendering or mutation.

The top-level message carries `schema_major` and `schema_minor`. Unknown majors are
rejected. Newer minors are accepted when Protobuf decoding succeeds and all semantics
required by the requested operation are understood. Mutation fails closed if replacement
semantics cannot be validated.

Generated bytes must be reproducible for the same pinned producer, schema/runtime, and declared
inputs. This is not a canonical encoding across producer builds, languages, or upgrades:
[Protobuf deterministic serialization is not canonical](https://protobuf.dev/programming-guides/serialization-not-canonical/).
Pin serializer inputs and normalize semantic ordering; compare decoded semantics for compatibility
and candidate consensus, not serialized envelope equality. Source and replacement digests still
identify exact file bytes, not Protobuf message identity.

## Result Identity

Each result identifies the configured producer target, capability, ordered stage/tool
identities, each stage's ordered semantic file-class IDs and exact direct-source paths, and
execution/convergence state. Audit results identify one tool adapter and its effective classes
and sources. One
action produces one result. Producer identity remains
internal; public output deduplicates diagnostics with identical exposed fields and sorts
them without exposing producer identity.

Exact field numbers, reserved ranges, and generated API names are frozen in
[`quality/result.proto`](../../quality/result.proto); that file is normative for the
allocation and this prose states the semantics. The semantic fields below are required
before that schema is approved.

## File Identity

Files are identified by normalized slash-separated paths relative to the main workspace.
Paths are valid UTF-8, lexical, non-empty, contain no `.` or `..` component, and remain
beneath the workspace root. Absolute paths, external artifacts, Bazel execution paths,
and owner labels are not source identities.

A source snapshot uses BLAKE3-256 over exact file bytes, stored as exactly 32 raw bytes.
There is no per-record digest algorithm enum. Changing the algorithm is schema-major.

## Diagnostics

Each diagnostic contains:

- `INFO`, `WARNING`, or `ERROR`; zero `SEVERITY_UNSPECIFIED` is invalid.
- Normalized message text.
- Stable tool identity and optional native/normalized rule identity.
- Optional workspace source path and half-open UTF-8 byte range.
- A required `fixable` boolean.

`start_byte` is inclusive and `end_byte` exclusive. Adapters normalize native coordinates
against the exact source snapshot. Invalid boundaries and out-of-range locations are
protocol failures. Line and column are not duplicated in the message.

`fixable=true` is a guarantee, not a tool-rule capability hint. It is valid only for an
initial diagnostic with a checked-in workspace path when the same converged result includes an
exact replacement for that path and the pipeline proves the finding is absent from the stable
terminal analysis because of that candidate. An adapter that lacks any part of this proof records
`fixable=false`; there is no unknown state. Fixability is never inferred because another
diagnostic or formatter changes the same file.

When identical initial finding records are collected through multiple owner/configured pipeline
contexts, the public deduplicated finding is fixable only if every contributing record
guarantees it and all contexts produce identical stable file candidates. This prevents
deduplication from strengthening a claim.

Generated and external artifacts may be read-only analysis context but are not source
identities. A finding attributed only to generated context is retained without a
workspace path/range and still participates in severity policy.

## Replacements

Pipeline results carry an initial diagnostic set, a terminal diagnostic set from the complete
no-change round, ordered stage identities, completed-round count, and convergence status.
Successful `STABLE` results may carry original-to-terminal replacements. `OSCILLATION` and
`ITERATION_LIMIT` are completed but non-applicable results: they identify the affected paths
and stage sequence, fail evaluation, and provide no workspace replacement. Tool launch,
configuration, native-output, or protocol failure still fails the Bazel action rather than
claiming completed convergence.

At most ten complete cross-tool rounds execute. A round includes every nonempty selected stage
in its measured ruleset order, and each stage operates on the fixed source subset recorded for
it. If round ten changes any virtual file, the result is
`ITERATION_LIMIT`; no eleventh round runs. Repeated-state detection after every changing stage
may produce `OSCILLATION` earlier. Native tool-internal iteration is part of that one stage
invocation and remains governed by the pinned tool rather than this cross-tool counter.

Replacement data is inline normalized byte-range edits. Each file edit set contains:

- Workspace path.
- Original BLAKE3-256 digest.
- Strictly start-byte-sorted, non-overlapping edits with distinct start offsets against the
  original bytes.
- Inclusive `start_byte`, exclusive `end_byte`, and replacement bytes per edit.

Source and replacement bytes must be valid UTF-8. Empty ranges insert and empty replacement
bytes delete. Each range satisfies `start_byte <= end_byte`, both offsets are at most the
source byte length, and both lie on UTF-8 code-point boundaries. Same-offset edits are invalid;
for each adjacent sorted pair, the preceding `end_byte` is at most the next `start_byte`, so
an insertion cannot sit inside a replaced range. Adjacent edits are valid. A formatter may
represent its output as one edit spanning the complete original file. An edit identical to its
original range and a complete candidate identical to its source are invalid no-ops.
Quality replacements only modify existing direct main-workspace non-generated sources; they cannot create or delete a
complete file in v1.

The shared Rust runner derives final edits by comparing stable action-local source copies with
their original bytes. Native stage edits are validated before changing virtual state. Adapters
do not implement independent diff, convergence, or final-normalization logic.

The CLI groups replacements by path, requires one original digest, deduplicates identical final
candidates from multiple producer contexts, and rejects candidate disagreement, digest
disagreement, invalid ranges, and stale current bytes. It does not merge edits from distinct
pipeline results because no producer validated the combined candidate. Each path is
an independent atomic mutation unit: failure rejects that path but does not block valid
unrelated paths, and any rejected path makes the overall command fail. Paths commit in
deterministic order, so interruption may leave complete earlier files applied and later files
untouched, but never a partially written file.

Check mode performs the same grouping, digest agreement, candidate consensus, range, and
current-source validation without applying the result. Its public `change` event exposes the
validated digest and exact edits. Default mode applies the same normalized set. Replacement
presence is therefore independent of the requested mutation mode.

Before mutating any path, the CLI validates complete selected-result collection and every
result envelope needed to determine the candidate path set. Missing, malformed, unsupported,
or incomplete results prevent all mutation. Invalid edit data attributable to one path is a
per-file rejection after that global validation boundary.

Only checked-in workspace sources may be direct analysis subjects or replacement
destinations. Generated and external context is always read-only.

## Execution And Policy

Adapters classify native exit codes that mean completed analysis with or without
findings. The runner records normalized diagnostics and completed status, then the Bazel
action succeeds. Unknown exit codes, signals, launch failures, invalid configuration,
malformed native output, and protocol violations fail the action.

Diagnostic severity does not determine producer action success. `dx` applies its
`--fail-on` threshold after collection. Direct Bazel CI enables one evaluator action per
result with `@rules_dx//config:validate=true` and selects the same threshold through
`@rules_dx//config:fail_on`. Evaluators emit validation markers or fail without rerunning
or aggregating analyzers. They also fail when a result proposes any replacement, independently
of diagnostic severity. Threshold-only changes do not invalidate expensive analyzer
actions.

Pipeline results describe both the original analyzed snapshot and the stable terminal snapshot.
Fix-capable stages do not remove initial findings after convergence; newly exposed terminal
findings are also retained with ranges relative to the terminal snapshot. The CLI combines
initial fixability, terminal findings, and the file mutation outcome to derive public resolution
and default-mode failure policy without rerunning analysis after local apply.

## Collection

BEP artifact processing is incremental, but each result is decoded as one message. The
collector validates schema, paths, digests, ranges, execution state, and referenced
semantics before rendering or planning mutations. It deterministically merges independent
results without retaining source contents solely for output.

Malformed or unsupported messages produce operational failure. Valid results from other
keep-going actions remain available for marked partial reports, but no mutation
is allowed.

## Compatibility Tests

Fixtures cover:

- Unknown major rejection and compatible minor additions.
- Unknown-field preservation behavior and required-semantic failure.
- Byte-identical outputs from the same pinned producer and inputs, separately from semantic
  compatibility across producer/schema upgrades and valid alternative wire encodings.
- Path normalization and traversal rejection.
- Multibyte UTF-8 boundaries and invalid ranges.
- Digest mismatch, duplicate final candidates, owner-context disagreement, same-offset edits,
  insertion within a replaced range, no-op edits/candidates, and prohibited creates.
- Invalid UTF-8 source or replacement bytes.
- Completed findings versus execution failure.
- Required binary fixability, rejection of unsupported true claims, conservative duplicate
  merging, and exact association with the validated same-file candidate.
- Stable stage order, full no-change completion, repeated-state oscillation, iteration limit,
  initial/terminal diagnostic provenance, and initial-to-final edit reconstruction.
- Deterministic candidate consensus independent of BEP and depset ordering.
- Remote output materialization without output-tree scanning.
- Parity between `dx` threshold evaluation and Bazel-owned per-result evaluators.
- Exact public check-mode changes reconstructed from validated internal replacements.

Result-side fixtures for the schema, versioning, path, digest-length, diagnostic-shape,
edit-ordering, and stability-gate items above live in `//rust/quality_result` and pass
under `bazel test //rust/quality_result/...`. CLI, BEP-ordering, remote-materialization,
and evaluator-parity items land with their WP2/WP3 owners.
